## Goal
Production (both servers share one Helius devnet key) is rate-limited: in 15 min the new server logged 345
`rpc call failed, retrying … getProgramAccounts() … status code: 429`, 133 `scheduler: list series` errors and 32
`upstream call failed` (the web shows "chain read failed"); the old server 465 × 429. Every scheduler tick and many API
requests re-scan program accounts (`internal/chain/client.go` `GetProgramAccounts`, used by AllSeries, open actions,
investors, entitlements, trade admissions; callers in `internal/scheduler`, `internal/api/{rest,showcase,admin,reports}.go`).

## Do
1. One cache at the single choke point `chain.Client.GetProgramAccounts`: key = discriminator + filters; TTL default 3 s
   (env `RPC_GPA_CACHE_TTL`, `0` disables); concurrent identical calls share one RPC request (singleflight —
   `golang.org/x/sync/singleflight` only if already in go.mod, otherwise a small mutex+wait map). Return copies so callers
   cannot mutate cached slices.
2. Freshness after writes: every CLI step changes chain state — invalidate the whole cache when an executor step finishes
   (hook from `internal/executor` `Run`/`RunRaw` completion, or the scheduler/sandbox call sites; one place, not per caller).
3. 429: `withRetry` (client.go:336) — on HTTP 429 back off exponentially with jitter (e.g. 0.5 s, 1 s, 2 s; honour
   `Retry-After` if the error exposes it) instead of the linear quick retry; other errors keep today's behaviour.
4. Tests: cache hit within TTL (one RPC call for two reads), miss after TTL, invalidation after an executor step,
   singleflight (N concurrent reads → 1 call), 429 backoff path (fake RPC). Keep every existing test green.
5. Worklog: expected call reduction (count gPA calls per scheduler tick before/after with the fake RPC).

## Review feedback (round 1, 2026-10-12 07:14) — fix every blocking item first; your previous work is already committed on this branch

### Summary
Small change at the right choke point, with good tests and correct 429 handling. One correctness gap blocks the merge: invalidation does not cover scans that are in flight, so a read started before a CLI step can repopulate the cache with pre-write state for up to 3 s. A generation counter (~8 lines plus one test) fixes it. Tests were not rerun here because Bash was denied; this relies on the orchestrator's green make verify.

### Blocking
- services/registrar/internal/chain/client.go:196 — Freshness after writes (AC 2) does not hold under concurrency. InvalidateProgramAccounts clears `entries` but not in-flight scans: a scan that started before a CLI step finished (e.g. a dashboard poll, or one stuck in 429 backoff for 0.5–2 s) completes after the invalidation, then stores its pre-write result with a fresh timestamp (`at: now()`). It also hands that result to every caller that joined the flight after the step, including the scheduler's next read. For up to the TTL (3 s, which is more than the 2 s demo tick), the scheduler can see pre-step state and re-submit the same step. That breaks the constraint of no behaviour change other than fewer RPC calls.
  **Fix:** Add a generation counter to gpaCache (`gen uint64`). Increment it in InvalidateProgramAccounts and also run `clear(c.cache.flying)` there, so new callers start a fresh scan instead of joining a stale flight. In GetProgramAccounts, capture `gen := c.cache.gen` under the lock when creating the flight. After the scan, write to `entries` only if `err == nil && c.cache.gen == gen`. Delete `flying[key]` only if it still points to this `fl`. Add a test: hold the first scan open on the fake server, call InvalidateProgramAccounts, release the scan, then read again and assert a second RPC call happens (calls == 2).

### Acceptance criteria not met
- Invalidate whole cache when an executor step finishes, in one place — Hook is in executor.exec via defer OnStepDone, covering Run and RunRaw, wired in main.go. Tested by TestStepDoneInvalidatesScanCache. But a scan in flight across the invalidation repopulates the cache with pre-write data (see blocking).
