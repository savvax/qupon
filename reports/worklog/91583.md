# 91583 — registrar survives the RPC rate limit

What changed (round 1 review fix on top of the committed cache):
- `gpaCache` gained a `gen` counter; `InvalidateProgramAccounts` bumps it and
  clears `flying`, so an in-flight scan started before a CLI step finished can
  no longer repopulate the cache with pre-write rows; the flight key is deleted
  only if that flight still owns it.
- New `TestGPACacheInvalidationDropsInFlightScan`: first scan held open across
  an invalidation → next read re-scans (rpc calls == 2).
- Round-0 work (already committed): 3 s TTL cache + singleflight in
  `chain.Client.GetProgramAccounts` (`RPC_GPA_CACHE_TTL`, 0 disables),
  executor-step invalidation hook (OnStepDone), 429 exponential backoff with
  jitter in `withRetry`.

Measured: one refresh cycle (scheduler tick + dashboard reads) = 8 gPA requests
uncached → 4 cached (`TestGPACacheCallReduction`); per-tick duplication gone.

What to watch: invalidation clears flights globally — a caller that joined a
pre-step flight still receives pre-write rows (same as no-cache-before-step);
429 backoff now sleeps up to ~2 s, so sandbox/dashboard reads can look slower
under sustained rate limiting.
