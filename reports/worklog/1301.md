# 1301 — secondary trades via Solana DvP: escrow admission and record-date guard

- New instructions `admit_trade` / `release_trade(force)` (registrar or paying agent), account `TradeAdmission`, counter
  `Series.open_trades` (4 bytes taken from `reserved`; size still 389, older series read 0); `strike_record` fails with
  `TradesInFlight` while the counter is non-zero. Three errors appended at the end of the enum (6030–6032).
- Qupon never CPIs into the DvP program: parties fund with plain transfers and the registrar signs `SettleDvp` /
  `CancelDvp` directly. We only thaw the bond escrow, after checking the `SwapDvp` record by fixed offsets (458 bytes,
  no discriminator — pinned to v0.1.0, fails closed if the size changes; the Foundation holds the upgrade authority).
- Why the guard: on devnet a paused mint blocked settle, cancel and reclaim alike (`reports/dvp-spike-2026-10-06.md`),
  and escrowed units have no Investor record, so `finalize_snapshot` could never reach Σ = supply.
- Review finding fixed before commit: the DvP cancel is atomic over both legs and reverts when a refund account is
  closed or frozen, so a party could keep `open_trades > 0` forever. `release_trade(force = true)` returns the escrowed
  units to the seller with the series PDA's permanent-delegate authority (test: seller closes their bond account).
  `admit_trade` also rejects redirected settlement destinations.
- Tests: `tests/trade.rs` (5) run the real devnet DvP binary in LiteSVM (`tests/fixtures/dvp_swap.so`, `make fixtures`)
  with a legacy-SPL cash leg. Codama client regenerated; `series.b64` re-exported (random keys only); Go event
  layouts for `TradeAdmitted` / `TradeReleased` and the pinned event count (18 → 20).
- Follow-ups queued as plan 13 (`docs/superpowers/plans/2026-10-06-plan13-secondary-trades-dvp.md`, tasks 1302–1306);
  the DvP IDL is vendored at `clients/ts/idl/` and the `// mount: trades` anchor is in `api.go` for them.
- To watch: redeploy before any CLI/UI task runs on devnet — the binary (589,192 bytes) no longer fits the program
  account (568,256), so it must be extended. A registry gap found on the way is fixed in the same
  branch as task 91301.
